## Summary answer (read first)

The golden-fixture gate is a **single reconcile test** (`test/golden/golden_fixture_test.dart`)
that replays a committed JSON dataset (`test/golden/astro_golden.json`, 37 cases across 6
sections) against the real pure-Dart astro engines in `lib/features/astro_engine/domain/`. It is
correctly wired as a **blocking Tier-1 CI check** (`.github/workflows/ci.yml:40` runs `test/golden/`
with no `continue-on-error`) and is picked up locally by `just validate-local`
(`scripts/validate-local.sh:35` runs the whole `flutter test --coverage` suite).

**The single most important finding is a provenance weakness, not a wiring weakness.** The
"expected" values in the fixture were **generated by calling the very same engine** the gate is
supposed to police — `tool/regen_golden.dart` runs each calculator and writes its output back as
the "known-correct" expectation (e.g. `tool/regen_golden.dart:62-72` for Moon longitude,
`:135-150` for nakshatra/bird). The `source` strings in the JSON (e.g.
`astro_golden.json:17` `"Jean Meeus ELP2000/82 (Ch. 47)"`) are **hand-written annotations**, not
evidence that the number was independently verified against Meeus or the CONF corpus. So the gate
is a **snapshot/regression lock** (it catches future *drift* from today's engine output) — it is
**not** an independent-ground-truth correctness proof. That is exactly the CONF/RC-gate concern
the brief flagged: nothing in the fixture proves today's frozen value is itself correct.

Secondary gaps: several engine branches are entirely unpinned — night yamas Y6–Y10
(`yama_calculator.dart:150-178` `calculateNight`), tattva outside `yama1`, the Sushumna/Yoga
alignment path in the Oracle (`oracle_engine.dart:116-118`), Emakandam lockout, and the full
5×5 bird state tables. Birth-bird coverage exercises only 5 of 27 nakshatras and 4 of 5 birds
(peacock is never asserted end-to-end).

## 3. Fixture provenance (the CONF/RC concern)

**How the expected values were produced:** every `expected` block in `astro_golden.json` is the
**output of the engine itself**, captured by `tool/regen_golden.dart`. The tool defines only the
*inputs* and hand-written `source`/`tolerance`, then calls the real calculator and writes whatever
it returns into `expected`:

- Moon: `tool/regen_golden.dart:62-72` — `MoonLongitudeCalculator.calculate(dt)` → `expected.longitude = res.longitude`.
- Nakshatra/bird: `:135-150` — `NakshatraCalculator.calculate` + `PakshiCalculator.birthBirdFromNakshatra` → `expected`.
- Swara: `:210-231`; Hora: `:289-309`; Tattva: `:362-392`; Oracle: `:519-543` — same pattern.
- The fixture's own `meta.note` states it plainly: `astro_golden.json:5`
  `"known-correct outputs; regen via tool/regen_golden.dart"`.

**Implication:** the gate is a **self-referential snapshot**. It freezes today's engine behaviour
(engine `v1.13.0`, `astro_golden.json:5`) and fails closed on future drift — genuinely valuable
as a regression lock. But the `source` lines are *claims of lineage*, not independent derivations:

- `moon-04` cites Meeus Example 47.a (`astro_golden.json:51`) — the only case whose expected
  number is in principle checkable against a published worked example; even there, the committed
  value `133.16265468515903` is the engine's output, not a transcription of Meeus's printed result.
- Every nakshatra case cites `CONF-PP-001 / CONF-PP-002 (canonical 5-6-5-5-6 star table)`
  (`astro_golden.json:77` etc.) and every swara/tattva/oracle case cites a CONF id, but the
  *value* was still produced by the engine, not read from the CONF document.

**Provenance flag (RC-gate):** **No fixture case carries independent ground truth.** All 37
expected values share the same provenance class — "engine snapshot, CONF-annotated." The README
is candid that regeneration recomputes from the current engine (`README.md:29-34`) and that
changing a value is a human decision (`README.md:25-26`), but there is no committed artifact (a
hand-computed table, a Meeus transcription, a CONF-extracted expected set) that would let a
reviewer confirm the frozen numbers are *correct* rather than merely *current*. This matches the
requirements' own framing that the Spec "pins the EXISTING resolved behavior" and adds "no new
doctrine" (`requirements.md` CONF row / R4.2) — i.e. it is explicitly a lock, not a proof.

The REPORT.md and `tasks.md` under `.kiro/specs/golden-fixture-gate/` were present at
investigation time (directory listing) and describe the same self-regenerating design.

## 4. Gap list (weak spots)

1. **Self-referential ground truth (highest concern, RC-gate).** Expected values are engine
   output (`tool/regen_golden.dart:62-72` and throughout), not independently derived. A latent
   bug already present at `v1.13.0` is frozen as "correct" and will never be caught by this gate.
2. **Night schedule Y6–Y10 entirely unpinned.** `YamaCalculator.calculateNight`
   (`yama_calculator.dart:150-178`) has zero golden cases; tattva reconcile only uses the daytime
   yama path (`golden_fixture_test.dart:338-341`).
3. **Tattva pinned only in `yama1` on one date** (`astro_golden.json:364-436`) — yama2–yama5
   element cycles unverified.
4. **Sushumna/Yoga-window alignment unpinned.** The `BreathFlow.sushumna` →
   `isSushumnaAligned` branch (`oracle_engine.dart:116-118`, `action_window.dart:58`) is never
   exercised; all oracle cases use solar/lunar (`astro_golden.json:446`+).
5. **Emakandam lockout unpinned.** Only Rahu Kaal floor-lock is tested (oracle-05); the parallel
   Emakandam path (`oracle_engine.dart:71`) has no case.
6. **Birth-bird table under-covered.** 8/27 nakshatras, 4/5 birds asserted; peacock only once;
   no end-to-end longitude→bird reconcile (§2.2).
7. **Hora cycle thin.** 2/7 day-lords and a small slice of the 24-hora Chaldean sequence pinned;
   day→night transition at the exact boundary untested (§2.4).
8. **Swara civil-day rollover unpinned.** No pre-dawn case exercises
   `SwaraClock.anchorSunrise` (`swara_clock.dart:140-176`); the late-day alternating-block flip
   (`swara_clock.dart:118-129`) is lightly covered.
9. **No deliberate boundary cases.** No Moon-longitude case near a nakshatra cusp — the
   `±1e-6°` tolerance's behaviour at a boundary is untested (acknowledged unresolved in
   `requirements.md` §4c).
10. **Location-anchored Oracle alignment unexercised** (`oracle_engine.dart:120-129`): every
    case omits lat/lng/utcOffset, so only the fallback anchor branch runs.
11. **Minor — loose-ish float asserts are actually fine.** Moon uses `±1e-6` and Oracle score
    `±1e-9` (`golden_fixture_test.dart:133`, `:420`); for integer scores this is effectively
    exact, so not a real looseness bug — noted for completeness.

Note on strengths (so the gate is not undersold): the fixture *integrity* guard is solid — a
missing section, empty list, or < 20 total cases fails immediately
(`golden_fixture_test.dart:67-102`), and every per-case path fails closed on a missing field or
null engine result rather than skipping (`:116-120`, `:258-259`, `:349-357`), satisfying R2.2.

## 5. PROPOSALS (non-binding — NOT applied in this run)

> These are recommendations only. Nothing below was implemented; no `lib/` or `test/` file was
> changed. A follow-up would be a **sprint-deliverable Spec** per
> `collaboration-guardrails.md:85` (§3.1) — the golden-fixture gate is named there as an
> engine-spine item requiring the full gate.

A hardening Spec (`fix/*` or a new `golden-fixture-gate-v2`) would want to:

1. **Introduce independent ground truth for a seed subset.** Commit a small hand-computed /
   corpus-extracted expected table (at minimum the Meeus 47.a longitude transcribed from the
   book, and a handful of CONF-table nakshatra→bird rows read straight from `CONF-PP-001/002`),
   and assert the engine against *those* literals — breaking the self-reference for the anchor
   cases. This is the direct answer to the RC/CONF concern.
2. **Add night-schedule cases (Y6–Y10)** covering `YamaCalculator.calculateNight` and a tattva
   reconcile inside a night yama, plus tattva cases across yama2–yama5.
3. **Add Sushumna + Yoga-window Oracle cases** (and an Emakandam-active case) so the
   `isSushumnaAligned` and Emakandam branches are pinned.
4. **Expand the bird table toward exhaustive** 27-nakshatra coverage (or at least ≥1 DOB per
   bird, with peacock appearing more than once) and add one longitude→nakshatra→bird end-to-end
   case.
5. **Add boundary cases** — a DOB/longitude placed deliberately just inside and just outside a
   nakshatra cusp — and confirm the `±1e-6°` tolerance behaves, resolving the open question in
   `requirements.md` §4c (with the owner's sign-off on the chosen tolerance).
6. **Broaden hora** to all 7 day-lords and at least one day→night boundary hora.
7. **Add a pre-dawn swara case** to pin the `anchorSunrise` civil-day rollover, and a late-day
   case to pin the alternating-block flip.
8. Keep R4 discipline intact: any *new* expected literal added by hand must cite its independent
   source in the PR (and Decision Journal / CONF where doctrinal), per `README.md:25-26`.

Each proposal above is additive (new fixture cases + new assertions); none requires changing
engine `lib/` logic. If any proposed case *fails* against the current engine, that is a revealed
bug and — per `requirements.md` R4.2 / §4 "Out of scope" — must be flagged to the owner as a
separate `fix/*` finding, not silently masked by regenerating the fixture.
